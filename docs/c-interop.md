# C interoperability

Flux can emit a C header for the current stable C export ABI. This package export boundary is Flux's stable C FFI surface today: native C code can call exported Flux functions and pass ABI-safe `Copy` callbacks directly into Flux. Flux can also import a deliberately narrow C-symbol subset on Linux, Android, and Windows. The supported boundary has explicit ownership rules: safe imports are pointer-free, borrowed pointer inputs/results require `unsafe extern c`, recursively `Copy` exports cross by value, and shapes without a defined ownership/lifetime contract are rejected rather than guessed. The versioning and platform-boundary rules are defined in `docs/native-abi.md`:

```sh
flux emit-c-header path/to/package -o flux_api.h
```

The header declares `FLUX_C_ABI_VERSION` (currently `2` for project/package compilation) so native consumers can pin the export contract they were compiled against. It contains declarations for `pub fn` exports, typedefs for public transparent aliases of supported ABI types, typed macros for public compile-time scalar constants, layouts for public `Copy` structs and enums used across the boundary, layouts for supported public closed `Copy` interfaces, `Copy` optional wrappers, and plain C function-pointer typedefs for ABI-safe `Copy` callback signatures. Private functions/constants and `main` are not exposed. Current supported ABI types are `i64`, `bool`, `str`, `error`, their supported `Copy` optionals, recursively copyable public structs whose fields are themselves supported ABI values, recursively copyable public enums whose payloads are supported ABI values, public closed interfaces whose complete implementation set is public and recursively ABI-safe, and function values whose parameters plus zero-or-one result are themselves ABI-safe `Copy` values, including recursively nested function values and supported interface values. Nested callback typedefs are emitted dependency-first so an outer function-pointer typedef can safely name its inner callback parameter/result type. Multiple return values lower to a generated C result struct whose fields are named `v0`, `v1`, and so on; fields and function signatures preserve a directly named public alias through generated `flux__alias_<Name>` typedefs. Chained public aliases preserve their declared alias relationship in the header, and alias dependencies are emitted before aliases that refer to them even when Flux source uses forward alias declarations.

`i64` lowers to `int64_t`, `bool` to C `bool`, and function `str` / `error` values lower to borrowed `const char *`. C callers must not free or retain those borrowed function-result pointers beyond the lifetime guaranteed by the Flux value that produced them. Public compile-time `str` constants instead expand to ordinary escaped C string literals with static storage duration.

Generated constants use compiler-prefixed names such as `flux__const_DEFAULT_LIMIT`. ABI v2 callable exports use deterministic package/module-qualified linker names of the form `flux__abi_<module-hex>__fn_<Name>`; `<module-hex>` is the lowercase hexadecimal encoding of the stable module identity documented by the package loader. For example, two packages that both export `parse` no longer publish the same linker symbol. Public struct and enum tags use the corresponding `flux__abi_<module-hex>__type_<Name>` form, preventing package headers with the same source-level value-type name from colliding. Public enum discriminant typedefs and constants are module-qualified as `flux__abi_<module-hex>__tag_<Name>` and `flux__abi_<module-hex>__tag_<Name>_<Variant>`. Generated C keeps its shorter internal source-level identifiers and binds callable exports to qualified linker symbols with compiler-owned assembler labels, while the generated header declares the qualified identifiers directly. Multi-return header struct tags use the same module qualification. The generated header is C++ compatible through an `extern "C"` block. Compiler regression coverage compiles generated package headers through both C11 and C++17 consumers and compiles package C output to an object before inspecting exported linker symbols, so source-level or module-identity changes cannot quietly desynchronize the foreign ABI.

Primitive `Copy` optionals cross by value as `struct flux__optional_<type> { bool has_value; T value; }`, exactly matching generated Flux C layout. They therefore add no hidden allocation, ownership transfer, drop, or aliasing obligation. Optional recursively ABI-safe public structs/enums use dependency-ordered wrappers with collision-safe package/module-qualified public identities, so they may appear in public fields, aliases, exported parameters/results, and ABI-safe callback signatures without inventing heap ownership.

Public `Copy` structs cross the boundary by value with their field order and compiler-owned C field names fixed by the generated header. Public `Copy` enums also cross by value: the discriminant is fixed to signed 32-bit storage, variants have deterministic zero-based tag constants, and payload variants use a compiler-owned C union/struct layout emitted in dependency order. Supported public closed interfaces cross by value using a deterministic closed-world layout over their complete public ABI-safe `Copy` implementation set. A single implementation can lower directly without a tag; multiple implementations use the generated tag-plus-union representation. The resulting layout, any required tags, optional wrapper, and use inside ABI-safe callback signatures are part of ABI v2. Because these exported values contain only recursively `Copy` ABI values, they do not create hidden ownership transfer, drop, or aliasing obligations for C callers. ABI-safe function values cross as plain C function pointers, so a C caller may pass a compatible native function into an exported Flux function and Flux may invoke it directly with no callback registry, serialization layer, or trampoline object. This applies recursively to callback parameters/results that are themselves ABI-safe function values because they remain `Copy` native function pointers rather than closure environments. Callback signatures containing lists, open/private interfaces, or other ownership-sensitive values remain rejected until those values have explicit foreign ownership/lifetime contracts.

## Ownership and lifetime contract

The safe import surface is intentionally pointer-free: ordinary `extern c` parameters/results are limited to `i64`, `bool`, and `void` where applicable. A borrowed `str` or `error` parameter or result crosses a native pointer boundary and therefore requires `unsafe extern c`. The declaration is the explicit lifetime trust boundary: borrowed inputs are valid for the duration of the call and native code must not retain them; borrowed results may be used only while the native API's documented lifetime remains valid. Flux does not silently copy, retain, free, or heap-box either side.

Values with no stable ownership contract are rejected even under `unsafe`: lists, interfaces, optionals/aggregates not covered by the stable export ABI, closure environments, and ownership-sensitive callback shapes cannot cross imported C boundaries. Imported foreign functions also cannot escape as first-class Flux function values; an ordinary Flux wrapper is required, keeping the unsafe boundary lexically visible. Exported recursively `Copy` values and callbacks cross by value with no transfer/destructor protocol, while borrowed exported strings remain non-owning pointers whose lifetime is documented above. This conservative rule set is the current safe FFI ownership model; adding future owned foreign strings/buffers will require an explicit allocator/drop contract rather than weakening these guarantees.

Linux, Android, and Windows packages can also import an existing C symbol directly without application-authored C/JNI/Win32 glue:

```flux
extern c "sqlite3_libversion_number" fn sqliteVersionNumber() -> i64
```

The quoted name is the exact linker symbol and the Flux function name is the typed source-level alias. Safe imports deliberately accept only pointer-free `i64`/`bool` parameters and `i64`/`bool`/`void` results. A native API that accepts or returns a borrowed C string/error pointer must use Flux's deliberately narrow unsafe escape hatch:

```flux
unsafe extern c "getenv" fn nativeEnv(name: str) -> str
```

`unsafe extern c` additionally permits borrowed `str` or `error` parameters and results. The declaration is an explicit trust boundary: Flux cannot prove whether native code retains an input pointer or how long a returned pointer remains valid, so the declared native contract must guarantee call-scoped input borrows and a sufficient result lifetime for every Flux use. Using `unsafe` for an otherwise pointer-free scalar/void import is rejected as unnecessary, and `unsafe` still does not admit aggregates, lists, optionals, interfaces, callbacks, or any other ABI shape whose layout/ownership contract is undefined. Imported functions may be called directly but cannot escape as first-class function values or implement Flux interfaces without an ordinary Flux wrapper. On Android this is the advanced NDK/native-library escape hatch only: ordinary Android framework access continues to use compiler-owned `android.*` bindings and generated JNI/JVM glue. On Windows, ordinary supported platform capabilities use compiler-owned typed `windows.*` bindings while `extern c` remains the direct escape hatch for ABI-safe native symbols. Neither path needs application-authored Java/Kotlin/JNI/Win32 bridge files, method channels, serialization buses, or a plugin registry.

Package `[native].libraries` and `[native].search_paths` supply validated linker inputs to Linux native builds, Android NDK builds, and Windows Clang targets. Search paths remain package-relative manifest data and library names remain logical `-l` names; Flux does not accept arbitrary linker command fragments through the manifest. Android resolves those inputs with the selected ABI's NDK Clang toolchain. A static third-party library may therefore be linked directly into `libflux.so`; dynamic dependencies are not automatically copied into APK/AAB outputs yet and must not be assumed bundled. All-ABI AAB builds require each configured native library to be linkable for every ABI being built (NDK/system libraries satisfy this naturally). Owned foreign values, richer imported signatures, and automatic redistribution of dependent shared objects remain future additive work; unsupported ownership shapes remain compile errors until those contracts exist.
