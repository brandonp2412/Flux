# Native and platform ABI compatibility

Flux separates source compatibility from binary compatibility. Grammar, formatter, package, diagnostics, and portable UI contracts have their own versions; native consumers must not infer binary compatibility from any of those versions.

The native/platform ABI policy itself is versioned as `NATIVE_ABI_POLICY_VERSION = 1` and is discoverable with:

```sh
flux abi --version
```

That command reports the compatibility-policy version, not a CPU architecture, Android ABI name, package-format version, or generated C export version. Tooling may use it to determine which binary-compatibility rules the installed Flux compiler follows.

## Stable public C export boundary

Manifest-backed package C exports currently use `FLUX_C_ABI_VERSION 2` in headers generated by `flux emit-c-header`. ABI version 2 covers the externally visible linker names, calling convention implied by the generated C declarations, supported scalar representations, recursively supported `Copy` aggregate layouts, enum discriminant representation and tag numbering, multi-return result layouts, callback function-pointer shapes, and the documented borrowed lifetime of `str` / `error` pointers.

A breaking change to any of those promises requires a new `FLUX_C_ABI_VERSION`. Examples include changing a public exported linker-name algorithm, reordering or changing the native representation of an exported aggregate, changing enum tag values/storage, changing ownership or lifetime obligations, or changing parameter/result ABI shapes. Additive compiler support for a new ABI-safe Flux type does not by itself break existing version-2 headers or binaries.

Direct single-source header emission retains the legacy `FLUX_C_ABI_VERSION 1` spelling because it predates package/module-qualified export identity. It remains useful for local embedding, but durable independently versioned native libraries should use manifest-backed packages and ABI v2 rather than relying on the legacy unqualified symbol namespace.

Generated headers are the authority for the C spelling and layout of an exported package. Native consumers should compile against the generated header and may statically reject an unexpected `FLUX_C_ABI_VERSION`.

## What is deliberately not stable yet

Flux does not claim a stable binary contract for values that `emit-c-header` currently rejects. Lists, interfaces, owned foreign values, ownership-sensitive resources, and other values whose move/drop/borrow rules are unfinished remain outside the stable public C ABI. Their eventual inclusion must define ownership and layout first; compiler-internal representations are not a substitute for that contract.

Generated C identifiers that are not declared by the public header are compiler implementation details. Private Flux functions, runtime helpers, anonymous-function helpers, UI backend helpers, tree-shaken metadata, and temporary/native cache internals may change between compiler releases.

## Platform ABI boundary

Flux follows each target platform's native ABI instead of inventing a framework-wide binary protocol. OS-required entry points and artifact conventions are stable only to the extent required by the target's documented support tier and platform ABI. For example, Android packages may expose framework-required native entry points and ABI-specific shared libraries, while Linux executables follow the selected native toolchain/target ABI.

Compiler-generated platform glue is private unless a Flux document explicitly marks a symbol or file format as a public interoperability contract. Java/JNI helpers generated for Android, GTK/native helper symbols on Linux, view/runtime helper names, and backend-specific internal layouts are therefore free to evolve without a Flux ABI-version bump. Portable Flux source APIs remain governed by their source/API compatibility contracts rather than by those private implementation details.

Future iOS, macOS, Windows, web/WASM, and additional native backends must follow the same rule: public foreign/native boundaries require an explicit versioned contract; compiler-owned bridge/runtime internals do not become public ABI merely because platform tooling can inspect them.

## Versioning rules

`NATIVE_ABI_POLICY_VERSION` changes only when these compatibility rules themselves change incompatibly. `FLUX_C_ABI_VERSION` changes when the public C export binary contract changes incompatibly. A compiler release may change private backend implementation details, optimization strategy, generated helper names, debug metadata, or tree-shaken internal layouts without changing either version.

When a future stable foreign boundary is introduced for another language or platform, it must expose its own concrete compatibility marker when the platform does not already provide a sufficient one, document ownership and layout obligations, and receive regression coverage before being described as stable.
